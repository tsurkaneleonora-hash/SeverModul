# SeverModul

SeverModul is a Russian-language demo website for a modular-home company. It includes a static chat interface and a Neon Function that searches a PostgreSQL knowledge base and can generate an answer with Groq.

## Project structure

- `index.html` — static website and browser-side chat interface.
- `src/index.ts` — Neon Function request handler, knowledge-base search, and answer generation.
- `001_initial_schema.sql` — PostgreSQL schema, indexes, and timestamp triggers.
- `002_seed_knowledge_base.sql` — example knowledge-base records.
- `favicon.svg` — site icon.
- `package.json` and `package-lock.json` — Node.js dependencies and scripts.

## Technologies

- HTML, CSS, and browser JavaScript for the static site.
- TypeScript and the Neon Functions runtime for the chat function.
- PostgreSQL, accessed through the `pg` Node.js package.
- Groq API for generated answers based on matching knowledge-base records.
- Netlify for manual publication of the static website.

## Environment configuration

The chat function uses `DATABASE_URL` and `GROQ_API_KEY` from its server-side environment. Telegram notifications use the server-only `TELEGRAM_BOT_TOKEN` and `TELEGRAM_CHAT_ID` variables. Do not put their values in browser code, commit them, or include them in issue reports.

The optional admin panel is served by the function at `/?action=admin`. Configure `ADMIN_PASSWORD` (at least 16 characters; use a randomly generated password) and `ADMIN_SESSION_SECRET` (at least 32 UTF-8 bytes) in the server-side Neon Function environment before enabling access. Keep these values in a password manager and enter them only through Neon Console; the panel does not display or edit secrets. The panel can view customer leads and conversations and can modify knowledge-base records, so restrict credentials and use it only against a branch whose data you are authorized to access. A branch cloned from production may contain production customer data.

The panel's Telegram check calls the bot's read-only `getMe` endpoint and does not send a Telegram message. Groq and Neon checks are also read-only. The health check reveals only `connected`, `not configured`, or `error` states.

Login throttling is stored in function memory per runtime instance; it is best-effort and does not coordinate across instances or survive restarts. Use a high-entropy administrator password and do not treat this throttle as a global brute-force control.

`.env.example` is a placeholder template and must not contain real credentials.

## Knowledge base

The function reads active records from the `knowledge_base` table. The SQL schema and example seed data are provided in the root directory. The seed content is demonstration material and should be verified before being used as real company information.

Records whose `source` starts with `demo_` are deliberately excluded from chat search. Add only verified company information to the active knowledge base; do not promote the demonstration seed records as factual content. The chat uses relevant records as its factual source and returns an explicit no-information response when none qualify.

## Chat API

- Send a message with `GET /?q=<message>&session_id=<uuid>`.
- Load the latest conversation history with `GET /?action=history&session_id=<uuid>`.
- Submit a manager request only after the visitor explicitly completes the chat form with `POST /?action=lead&session_id=<uuid>` and a JSON body containing `name`, `contact`, and `question`. The function associates the request with the session's open conversation and saves it with status `new`; the browser never connects directly to PostgreSQL.
- After a lead insert commits successfully, the function sends its ID, timestamp, status, name, contact, and question to Telegram using server-only `TELEGRAM_BOT_TOKEN` and `TELEGRAM_CHAT_ID` variables. Telegram delivery failures are logged by category without customer data and do not change the successful lead response. The response confirms only that the lead was saved, not that Telegram delivery succeeded.
- The history endpoint returns up to 100 messages from the most recent open conversation for that session. The session UUID is generated by the browser and persisted locally.
- Retry a failed message with `retry=1`; the function avoids storing an already-recorded matching user turn twice and returns a saved answer when the previous attempt completed.
- The function supports a CORS preflight for the JSON lead request. A successful response is shown as confirmation only after the database insert succeeds.

## Publication

The static website is published manually through Netlify. The Neon Function is deployed separately. Never upload `.env`, `node_modules`, local credentials, or local tooling configuration as website assets.

## Neon Function build

- `npm test` runs both the function and chat regression suites.
- `npm run typecheck:function` checks the handler with Node.js type definitions.
- `npm run build:function` bundles `src/index.ts` for Node.js 24 as ESM, smoke-tests the bundle without database credentials, and creates `dist/severmodul-neon-function.zip`.
- The ZIP contains only the root `index.mjs`. It does not contain `.env` files or environment variable values. The test deployment must receive its own branch-scoped `DATABASE_URL` from Neon and a separately configured `GROQ_API_KEY`.
- Configure `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`, `ADMIN_PASSWORD`, and `ADMIN_SESSION_SECRET` only in the server-side environment of the intended Neon Function. Never add them to the static site, client JavaScript, or repository. When adding or updating Neon Function environment variables, verify Neon Console's behavior for existing variables first so `GROQ_API_KEY` and `DATABASE_URL` are retained.
- The current handler expects the `users`, `conversations`, `messages`, and `knowledge_base` columns declared in `001_initial_schema.sql`. Confirm that the target test branch has this schema before deployment; this build does not inspect or modify any Neon database.
- Do not deploy the prepared archive until the target Neon project, test branch, function slug, and test-only secrets have been explicitly confirmed.

## Local Windows development network

On Windows, start the local proxy first. From a PowerShell session, enter the project and dot-source the setup script:

```powershell
cd "C:\Users\ThinkBook\Documents\мод.дом.чат"
. .\scripts\start-dev.ps1
```

The script checks the local proxy at `127.0.0.1:10809`, sets `HTTP_PROXY`, `HTTPS_PROXY`, and `NODE_OPTIONS=--use-env-proxy` for the current PowerShell process only, and verifies Node.js, npm, Neon CLI OAuth access, and read-only access to the configured test project and branch. It does not change Windows proxy settings, credentials, cloud resources, or deployment state. If the proxy is unavailable or Neon is listed in `NO_PROXY`, setup stops rather than continuing through a direct route.

Run the standalone network check with:

```powershell
.\scripts\check-network.ps1
```

It checks DNS, the local proxy socket, TLS-validated HTTPS access through the proxy, and Node.js `fetch` with proxy support. The anonymous API request may return HTTP 401; that confirms an HTTPS/API response and is not an authenticated access check. npm commands run from the prepared PowerShell session inherit the Node.js proxy option. Close the session to discard these process-only settings.
